## 二、SQL 方言对照

`query.py` 生成的 SQL 只有 8 类构造,逐一核对。**好消息**:全部 SQL 走 f-string 内联,**不用占位符**,所以 `%s` / `?` 的差异影响很小,只要 `execute(sql, params)` 签名兼容即可。

| 构造 | 出现位置 | PG | MySQL | SQLite | DuckDB | 备注 |
|---|---|---|---|---|---|---|
| `SUBSTR(col,1,7)` | query.py L203 趋势取月 | ✓ | ✓ | ✓ | ✓ | **仅当日期列是字符串**;date 类型全挂 |
| 日期字符串比较 `>= '2025-11-01'` | `resolve_period` 生成的 where | ✓ | ✓ | ✓ | ✓ | text 列通用;date 列靠隐式转换,可能用不上索引 |
| `ROUND(x/10000, 2)` | L125 | ✓ | ✓ | ✓ | ✓ | 整数列会**整除截断**,见陷阱 2 |
| `NULLIF(SUM(x) OVER (),0)` | L248–249 占比 | ✓ | 8.0+ | 3.25+ | ✓ | MySQL 5.7 不支持窗口函数 |
| `LIMIT n` | L271 topn | ✓ | ✓ | ✓ | ✓ | SQL Server / Oracle 要改 `TOP` / `ROWNUM` |
| `ORDER BY value DESC`(别名排序) | 多处 | ✓ | ✓ | ✓ | ✓ | SQL Server 不支持按别名排 |
| `col IN ('a','b')` | L147/150/187 | ✓ | ✓ | ✓ | ✓ | 字符串字面量,通用 |
| `COUNT(*)` / `MAX(col)` | `db_adapter` 锚点与行数 | ✓ | ✓ | ✓ | ✓ | 通用 |

**适配器要点**(三种常见引擎):

| 引擎 | 驱动 | 连接参数差异 | 占位符 |
|---|---|---|---|
| MySQL | `PyMySQL` | `database=` 而非 `dbname=`;要 `charset="utf8mb4"` | `%s` |
| SQLite | 内置 `sqlite3` | 只接文件路径;线程安全要设 `check_same_thread=False` | `?` |
| DuckDB | `duckdb` | 接文件路径或 `:memory:`;可直接读 parquet | `?` |

## 三、四个「不报错但出错数」的陷阱

这四条按危险程度排。引擎切换最怕的不是报错,是**静默出错**——数字看着正常,口径全偏了。

### 陷阱 1:日期列类型(最容易被忽略)

当前技能**硬假设** `trans_date` 是 `text` 且格式为 `YYYY-MM-DD`(`metric_cards.yaml` L13 已注明)。三处依赖它:

- `SUBSTR(trans_date,1,7)` 取月(趋势、月度矩阵)
- 字符串范围比较做期间过滤
- `anchor_date()` 取 `MAX(trans_date)` 当"今天"

新库若是 `DATE` / `TIMESTAMP` 类型,`SUBSTR` 直接报错(PG/MySQL)或返回怪值(SQLite 会转字符但不一定是 ISO)。**处理办法二选一**:

1. 在适配器里做类型归一(SQL 层加 `TO_CHAR` / `DATE_FORMAT` / `strftime`,或给每种构造注册方言函数)
2. 建视图时就把日期转成 text ISO(推荐,改动最小、口径最稳)

### 陷阱 2:整数除法截断

`ROUND(SUM(if_ape)/10000, 2)` 在 PG 里若 `if_ape` 是 **integer**,会先做整数除法再 `ROUND`,小数全被吃掉。MySQL 同理。SQLite 会转浮点所以不犯。
**处理**:分母写成 `10000.0`,或先 `CAST(col AS DECIMAL)`。改完必须验一条:APE 小数位是否还在。

### 陷阱 3:考核年起点

`resolve_period()`(query.py L77–103)把「2026 考核年」硬编码为 `2025-11-01 ~ 2026-10-31`。新库如果是自然年、或财年从 1 月/4 月起:

- **不会报错**,只会静默按 11 月切,所有期间口径全错
- **必须**改这段逻辑,并且**同步改**专家层口径红线(`agents/data-guide-agent.md` 的「考核年制」条目)

### 陷阱 4:渠道 / 机构取值不同(最容易出"0")

`WHERE channel_name = '银保'` 如果新库取值是 `bancassurance`,查询**成功返回 0 行**,展示成「0 万」,看起来像业务归零而不是配置错。
**验收必做**:切换后跑一次全渠道对比,任一渠道为 0 就说明取值映射错了。

## 四、执行顺序(别打乱)

1. **先读新库结构**:确认表名、字段名、日期列类型、渠道/机构取值清单。不确定就用只读账号跑 `SELECT DISTINCT channel_name` 之类的勘查查询
2. **写适配器 + 注册**:在 `db_adapter.py` 加类,`REGISTRY["mysql"] = MySQLAdapter` 这样登记
3. **配一份临时 config**:用环境变量指到新库,不动 `config.local.yaml`
   ```bash
   export DGA_DB_TYPE=mysql DGA_DB_HOST=... DGA_DB_NAME=... DGA_DB_USER=... DGA_DB_PASSWORD=... DGA_TABLE=policy_detail
   ```
4. **空跑冒烟**:`doctor.py` 全绿 → `query.py --intent menu` 能出菜单 → 单指标查询能返回非 0
5. **对账**(第五节):5 条基准查询逐条比对新旧库,数字必须一致或差异可解释
6. **正式切换**:把参数写进 `config.yaml` + `config.local.yaml`,删掉临时环境变量,再跑一遍医生与对账
7. **更新文档与专家层**:`迁移指南.md` 的数据库章节、`agents/data-guide-agent.md` 的口径红线(若考核年变了)

> 顺序的关键:**先环境变量试、最后才落配置文件**。写进 config 就等于切换完成,出错时排查面会变大。

## 五、对账金标准

拿**当前库的真实结果**做金标准(2026-11-10 实测),新库切换后逐条比:

| # | 查询 | 期望值 | 验的是什么 |
|---|---|---|---|
| 1 | `--intent single --metric ape --period 2026-09 --channel 银保` | **776.45 万元** | 基本连通 + 渠道过滤 + 万元换算 |
| 2 | `--intent yoy --metric ape --period 2026YTD --channel 银保` | 本期 **42,444.19** / 上年同期 **53,386.45** / 同比 **-20.5%** | 考核年窗口 + 上年同期偏移 |
| 3 | `--intent trend --metric ape --period 2026YTD --channel 银保` | 11 个月,2026-06 = **8,671.66**、2026-07 = **1,335.75** | 日期列类型 + `SUBSTR` 取月 |
| 4 | `--intent share --metric ape --period 2026YTD --channel 银保 --dim single_premium_flag` | 期缴 59.0% / 趸缴 41.0%(25,059.32 / 17,384.87) | 维度映射 + 窗口函数占比 |
| 5 | `doctor.py` 行数与锚点 | **721,080 行** / 锚点 **2026-09-10** | 表对不对、数据是否同一批 |

**差异判定**:

- 5 条全对 → 迁移完成
- 第 1/2 对但第 3 错 → 大概率日期列类型问题(陷阱 1)
- 第 1 对但第 4 错 → 维度列映射错
- 全是 0 → 渠道/机构取值不匹配(陷阱 4)
- 数字差一点点(如 776.45 → 776.00) → 整数除法截断(陷阱 2)
